\begin{abstract}
Vision-Language-Action (VLA) models predict robot actions from images and instructions, but no runtime safety layer exists for their outputs.
OpenVLA sends raw neural network outputs directly to motors; LeRobot's only guard is an imperative per-action check with no composition guarantees.
We show that SmolVLA outputs routinely violate expected action bounds on LIBERO -- whether from normalization mismatches, distribution shift, or model error, the consequence is the same: unsafe motor commands that no existing tool catches.
We introduce \texttt{SafeContract}, a design-by-contract framework that wraps any VLA policy with composable safety constraints via a Python decorator.
We show that stacked contracts (per-joint bounds, velocity limits) compose via intersection and that deadlock is unreachable from safe states.
The full decorator adds ${\sim}$13\,$\mu$s overhead per action -- less than 0.0001\% of VLA inference time -- requiring no QP solver, VLM, or model retraining.
For box constraints, SafeContract produces outputs identical to CBF-QP methods like AEGIS (which reports 0.36\,ms~\cite{aegis}) while requiring only clipping.
We provide a safety-fidelity Pareto analysis and component ablation on synthetic sequences, and release the framework as an open-source, pip-installable toolkit.\footnote{Code: \url{https://github.com/krishnam94/vla-edge}}
\end{abstract}

\section{Introduction}

VLA models~\cite{openvla,smolvla} enable robots to follow natural language instructions by predicting actions from visual observations.
Deploying these models to real robots faces a critical safety gap: \textbf{no runtime safety layer exists for VLA action outputs}.

This is not a theoretical concern.
OpenVLA's official deployment script sends raw neural network outputs directly to robot motors with zero bounds checking~\cite{openvla}.
LeRobot's~\cite{lerobot} \texttt{EEBoundsAndSafety} processor is the only existing runtime check, but it is imperative (called explicitly per action), provides no composition guarantees, and is easy to omit.
In practice, action space mismatches between training and deployment are common: multiple GitHub issues across OpenVLA and LeRobot document cases where wrong-scale commands reached hardware.\footnote{Representative issues: OpenVLA \#150 (action scale mismatch), LeRobot \#819 (no Jetson safety), \#3146 (no export pipeline for safe deployment).}
When a VLA trained on one robot's action space is deployed on another -- or when distribution shift causes extreme outputs -- the physical consequences range from motor stall to mechanical damage.

We demonstrate the problem empirically.
Running SmolVLA~\cite{smolvla} on 100 consecutive LIBERO~\cite{libero} observations, \textbf{every observation produces at least one action dimension outside $[-1, 1]$}, with values reaching 3.70.
This finding primarily reflects a normalization mismatch (SmolVLA was trained on SO-100 data, not LIBERO's normalized space), but this is precisely the class of deployment error that needs catching: the mismatch is invisible without runtime validation, and the wrong-scale commands would be sent directly to motors.

We introduce \texttt{SafeContract}, a design-by-contract~\cite{meyer1992} framework for VLA policies with three contributions:
\begin{enumerate}
    \item A \texttt{@safety\_contract} Python decorator that enforces composable safety constraints (per-joint bounds, velocity limits) on any VLA \texttt{predict()} method at runtime. One line of code wraps any policy.
    \item Composition properties showing that stacked contracts compose via intersection (Property~\ref{prop:composition}) and that the feasible set is always non-empty from safe states (Property~\ref{prop:deadlock}). While individually straightforward, these properties are non-obvious when multiple constraints interact in deployment, and no prior VLA safety system formalizes them.
    \item Empirical evaluation on synthetic and real VLA action sequences, including a safety-fidelity Pareto analysis that helps practitioners choose appropriate constraint strictness, and comparison against AEGIS-style CBF-QP enforcement~\cite{aegis}.
\end{enumerate}

\textbf{Why not just \texttt{np.clip}?}
Three reasons: (1) nobody does even this -- OpenVLA has zero bounds checking and no VLA codebase implements velocity limiting; (2) correct enforcement requires careful ordering -- velocity clamping after bounds clipping can push actions back outside bounds, requiring a re-clip (Section~\ref{sec:enforcement}); (3) the decorator pattern provides composability with guaranteed properties that ad-hoc clips do not.

\section{Method}

\subsection{Safety Contracts}

A safety contract $C = (\mathbf{l}, \mathbf{u}, v_{\max})$ specifies per-joint action bounds and a velocity limit:
\begin{itemize}
    \item \textbf{Per-joint bounds}: $l_i \leq a_i \leq u_i$ for each joint $i$
    \item \textbf{Velocity limit}: $\|\mathbf{a}_t - \mathbf{a}_{t-1}\|_\infty \leq v_{\max}$
\end{itemize}

\subsection{Enforcement Order}
\label{sec:enforcement}

Enforcement proceeds in three phases: (1)~clip to per-joint bounds, (2)~clamp velocity (project each joint's delta onto $[-v_{\max}, v_{\max}]$), (3)~re-clip to bounds.
The final re-clip is critical: velocity clamping shifts actions relative to the previous timestep, which can push them outside the original bounds.
Without this step, a single velocity clamp can produce out-of-bounds actions -- a subtle bug that naive implementations miss.

\begin{equation}
    \text{clip}(\mathbf{a}, \mathbf{l}, \mathbf{u})_i = \min(\max(a_i, l_i), u_i)
\end{equation}

The decorator pattern means any existing VLA adapter gains safety with one line:

{\small
\begin{verbatim}
@safety_contract(action_range=[-1,1],
                 joint_velocity_max=0.1)
def predict(self, image, instruction):
    return self.model(image, instruction)
\end{verbatim}
}

Three modes are supported: \texttt{clip} (silently enforce), \texttt{warn} (log violations), and \texttt{raise} (halt on violation). All violations are logged with timestep, dimension, magnitude, and severity for post-hoc analysis.

\subsection{Composition Properties}

Practitioners often stack constraints from different sources (hardware limits, task velocity bounds).
We show that stacking neither creates conflicts nor depends on order.

\begin{property}[Composition via Intersection]
\label{prop:composition}
For hyperrectangular contracts $C_1 = (\mathbf{l}_1, \mathbf{u}_1)$ and $C_2 = (\mathbf{l}_2, \mathbf{u}_2)$, sequential clipping equals intersection clipping:
$\text{clip}(\text{clip}(\mathbf{a}, C_1), C_2) = \text{clip}(\mathbf{a}, C_1 \cap C_2)$
where $(C_1 \cap C_2)_i = [\max(l_{1,i}, l_{2,i}),\; \min(u_{1,i}, u_{2,i})]$.
Consequently, stacking multiple \texttt{@safety\_contract} decorators is order-independent.
\end{property}

\textit{Proof.} Follows from the idempotence and commutativity of per-dimension $\min$/$\max$ operations. \hfill $\square$

\textit{Note:} This property covers stacking multiple decorators with per-joint bounds. The internal enforcement pipeline (clip, velocity-clamp, re-clip) is a fixed sequence within each decorator, not covered by this property.

\begin{property}[Feasibility from Safe States]
\label{prop:deadlock}
Let $\mathbf{a}_{t-1}$ satisfy contract $C$ with $v_{\max} > 0$. Then the feasible set $\mathcal{F}_t = \{\mathbf{a} : \mathbf{l} \leq \mathbf{a} \leq \mathbf{u}\} \cap \{\mathbf{a} : \|\mathbf{a} - \mathbf{a}_{t-1}\|_\infty \leq v_{\max}\}$ is non-empty.
\end{property}

\textit{Proof.} Since $\mathbf{a}_{t-1} \in [\mathbf{l}, \mathbf{u}]$ and $\|\mathbf{a}_{t-1} - \mathbf{a}_{t-1}\|_\infty = 0 \leq v_{\max}$, we have $\mathbf{a}_{t-1} \in \mathcal{F}_t$. The ``hold position'' action is always feasible. \hfill $\square$

\section{Related Work}

\textbf{Training-time safety.}
SafeVLA~\cite{safevla} fine-tunes with constrained RL (83\% violation cost reduction); RobustVLA~\cite{robustvla} adds Jacobian regularization.
Both require retraining; SafeContract wraps any pretrained VLA and is orthogonal.

\textbf{Inference-time enforcement.}
AEGIS~\cite{aegis} solves a CBF-QP at runtime (0.36\,ms) using VLM scene understanding and depth sensing.
Safety Chip~\cite{safetychip} uses LTL monitors for plan-level constraints.
SafeDiffuser~\cite{safediffuser} and CoDiG~\cite{codig} embed barriers in diffusion denoising but are restricted to diffusion policies.
ATACOM~\cite{atacom} projects onto constraint manifolds for pi0 and Octo.
SafeContract differs: (i)~architecture-agnostic (autoregressive~\cite{openvla} and flow-matching~\cite{smolvla}); (ii)~explicit composition properties; (iii)~pure clipping (${\sim}$13\,$\mu$s), no QP/VLM/depth sensor needed.
The tradeoff: action-space constraints only, not scene-aware; complementary to AEGIS.

\textbf{Robustness benchmarks.}
LIBERO-Plus~\cite{liberoplus} and VLA-Arena~\cite{vlaarena} diagnose VLA brittleness; SafeContract prevents the physical consequences at runtime.

\section{Experiments}

We evaluate SafeContract with two types of experiments: (1) real SmolVLA~\cite{smolvla} inference on LIBERO~\cite{libero} observations to demonstrate the problem (EXP-A), and (2) synthetic action sequences to evaluate contract properties in controlled settings (EXP-B through EXP-F).
All SmolVLA experiments use verified, queue-flushed inference -- SmolVLA caches 50 actions per VLM call, and failing to call \texttt{policy.reset()} before each new observation returns stale cached actions.
Platform: Apple M3, CPU, Python 3.12.

\subsection{VLAs Produce Unsafe Actions (EXP-A)}
\label{sec:exp_a}

We run SmolVLA on 100 consecutive LIBERO observations, calling \texttt{policy.reset()} before each to flush the action cache and force a fresh VLM forward pass.

\textbf{Result}: 100\% of observations produce at least one out-of-bounds action dimension.
Action values range from $-2.16$ to $3.70$ (expected $[-1, 1]$).
SafeContract detects 544 total violations: 121 per-joint bounds violations and 423 velocity violations ($v_{\max} = 0.1$).
Fig.~\ref{fig:action_ranges} shows the per-dimension breakdown.

\textbf{Normalization caveat.}
SmolVLA was trained on SO-100 robot data, whose action space differs from LIBERO's normalized $[-1, 1]$ range.
The 100\% OOB rate primarily reflects this normalization mismatch rather than model instability.
However, this is exactly the class of deployment error SafeContract is designed to catch: action space mismatches between training data and target robot are common in practice~\cite{openvla}, invisible without runtime validation, and send wrong-scale commands directly to motors.
Without a safety layer, the first indication of mismatch is physical damage.

\subsection{Method Comparison (EXP-B)}

We compare four approaches on 200 synthetic 7-DOF action sequences drawn from $\mathcal{N}(0, 1.5^2)$ (heavy-tailed to stress-test safety methods):

\centering
\caption{Method comparison on 200 synthetic action sequences. SafeContract catches velocity violations that naive clipping misses entirely.}
\label{tab:comparison}
\begin{tabular}{lcccc}
\toprule
 & No Safety & Naive Clip & \textbf{SafeContract} \\
\midrule
OOB rate & 99\% & 0\% & 0\%  \\
Vel.\ violations & unchecked & 199 missed & \textbf{0 (all caught)} \\
Total caught & 0 & 0 & \textbf{2{,}019} \\
\bottomrule
\end{tabular}
\end{table}

Naive \texttt{np.clip} enforces bounds (OOB drops to 0\%) but is blind to velocity violations: 199 of 200 timesteps have at least one joint exceeding $v_{\max} = 0.1$, and no violations are detected or logged.
SafeContract catches all 2{,}019 violations (680 bounds + 1{,}339 velocity) and enforces both constraints jointly.

\textbf{Comparison to AEGIS.}
For box constraints (per-joint bounds), SafeContract's clipping produces outputs \emph{mathematically identical} to solving the CBF-QP that AEGIS formulates~\cite{aegis} -- because the QP solution for box constraints is simply clipping.
The difference is overhead: AEGIS reports 0.36\,ms for its QP solver (which also handles non-box, scene-aware constraints via VLM); SafeContract's full decorator overhead is ${\sim}$13\,$\mu$s (Section~\ref{sec:overhead}).
The approaches are complementary: SafeContract handles action-space constraints cheaply, while AEGIS handles scene-aware obstacle avoidance.

\subsection{Composition and Ablation (EXP-C, EXP-F)}

We verify Property~\ref{prop:composition} and ablate contract components on synthetic sequences.
Three individual contracts (bounds-only: 680 violations, velocity-only: 1{,}339, joint subrange: 448) compose additively: the full contract catches 2{,}467 -- the exact union (Fig.~\ref{fig:ablation}).
This is by construction: each constraint check is independent and composition adds checks without interference.
Practitioners can stack contracts from different teams without worrying about interaction effects or order dependence.

\subsection{Safety-Fidelity Pareto Frontier (EXP-D)}

Tighter contracts catch more violations but clip actions more aggressively, distorting the policy's intended output.
We sweep 5 strictness levels on 200 synthetic sequences (Fig.~\ref{fig:pareto}):

\begin{figure}[t]
    \centering
    \includegraphics[width=\columnwidth]{figures/fig2_pareto.pdf}
    \caption{Safety-fidelity tradeoff. Very loose ($\pm 3.0$, $v_{\max}{=}1.0$): 948 violations, 0.03 mean clip. Very tight ($\pm 0.3$, $v_{\max}{=}0.02$): 2{,}561 violations, 0.91 mean clip. Practitioners choose the operating point for their risk tolerance.}
    \label{fig:pareto}
\end{figure}

This Pareto analysis provides concrete guidance: for a typical manipulation task with $[-1, 1]$ action space and $v_{\max} = 0.1$, the ``moderate'' operating point catches 2{,}019 violations with mean clipping of 0.45 -- correcting actions by less than half a unit on average.

\section{Discussion}

SafeContract provides a lightweight, composable safety layer for VLA deployment: one-line adoption, composable stacking, ${\sim}$13\,$\mu$s overhead.
The Pareto analysis (Fig.~\ref{fig:pareto}) gives practitioners a principled way to choose constraint strictness.
The limitation mirrors the strength: action-space constraints only, not scene-aware obstacle avoidance. Complementary to AEGIS~\cite{aegis}.

\textbf{Limitations.}
(1)~EXP-B through EXP-F use synthetic sequences; real VLA distributions may differ.
(2)~No closed-loop evaluation -- aggressive clipping could degrade task success. This is the most important next step.
(3)~The 100\% OOB finding primarily reflects normalization mismatch, not model instability; we present it as evidence that deployment errors are invisible without runtime checking.
(4)~Overhead measured on Apple M3 CPU; Jetson numbers may differ.

\textbf{Future work.}
Closed-loop LIBERO evaluation with task success rates.
Real-robot validation on Jetson Orin Nano.
Phase-adaptive contracts and conformal prediction for probabilistic safety certificates.
